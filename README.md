# 看门狗 KanmenDog

检测 **飞牛 fnOS（x86）死机并自动重启**的看门狗守护进程。当系统卡死（必须手动拔电才能恢复）时，由**内核看门狗硬件**强制复位；同时提供 **Web 管理页面**，可在浏览器里自定义检测参数、查看日志、一键开关。

> 仓库：https://github.com/gzywd/kanmendog ｜ 飞牛应用标识：`com.gzywd.kanmendog`

## v1.2.0：零误杀重构（升级必读）

本版本的设计哲学一句话：**宁可 3 分钟后才发现死机，绝不把正常使用/升级/重启误判成死机。**

| 场景 | v1.1.0 行为 | v1.2.0 行为 |
|---|---|---|
| 应用中心停止 / `systemctl stop` / 正常关机重启 | 进程被杀，看门狗未解除 → **约 60 秒后被硬件看门狗意外硬复位** | SIGTERM 处理器先 magic close **安全解除看门狗**再退出（systemd 单元配合 `KillMode=mixed` + `TimeoutStopSec=45`） |
| 飞牛系统升级（apt/dpkg） | 升级期高负载/D 状态/探针失败照常计数 → 可能误判重启、**打断升级** | 检测到 dpkg 锁/升级进程 → **继续喂狗但绝不判定**；判定达阈值的瞬间若在维护窗口，放弃重启并清零计数 |
| systemd 关机/重启流程进行中 | Web 探针等服务停止会失败 → 可能误判 | 检测 `/run/systemd/shutdown` → 同上，暂停判定 |
| 刚开机（fsck/服务初始化） | 高负载/D 状态偏高即计数 | **开机冷却期（默认 5 分钟）**只喂狗不判定 |
| 单次健康检查抖动 | 失败即停止喂狗，硬件看门狗倒计时启动 | **判定与喂狗解耦**：失败期间持续喂狗，只有决定重启才停喂 |
| 判定阈值 | 3 个周期（约 30 秒） | **18 个周期（3 分钟）连续异常**才判定 |
| 负载检查 | 默认开启（阈值 16） | **默认关闭**（高负载 ≠ 死机；可在页面手动开启） |
| 内存阈值 | 可用 < 5% | 可用 < **2%** 且持续 3 分钟（page cache 可回收，5% 会误杀大拷贝场景） |
| D 状态阈值 | 20 | **30** 且持续 3 分钟 |
| 服务探针 | 默认开启、命令硬编码 80 端口（fnOS 真实端口是 5666/8000，**必然误判**） | **默认关闭**；安装时自动探测 fnOS 管理端口（5666/8000/80/5667/8001/443）预填命令，开关交给用户，页面有醒目警告 |
| softlockup_panic | =1（高负载/虚拟化下有假阳性 → panic 误重启） | **=0**（保留 hardlockup_panic=1，几乎无误报）；四个内核参数**全量备份**，卸载逐项恢复（幂等，备份丢失时恢复默认值） |

> 真死机时本进程与 systemd 一并被冻结，SIGTERM 处理器不会执行，fd 保持打开且停止喂狗 —— 硬件看门狗照常兜底复位。**防误杀与死机兜底两不误。**

## 为什么需要它

真正的"硬死机"时，同一台机器上的任何用户态脚本也跑不动——它自己也被冻住了。唯一的可靠手段是**独立于内核调度的硬件定时器**：用户态守护进程定期"喂狗"，一旦卡死不再喂狗，硬件看门狗倒计时归零就强制重启。

本应用严格复用飞牛底层系统已有的"轮子"，不重复造：

| 轮子 | 作用 |
|---|---|
| 内核看门狗 `/dev/watchdog`（`iTCO_wdt` 硬件 / `softdog` 软件） | 终极复位，独立于内核调度 |
| systemd（`Restart=always`） | 守护进程挂了自动拉起（飞牛自带机制）；停止时优雅解除看门狗 |
| 内核 lockup 检测 `hardlockup_panic` | 把 CPU 硬锁死转成 panic → 自动重启 |
| `/proc/loadavg`、`/proc/*/stat`、`fork`、dpkg 锁 | 健康检查与维护窗口检测原语 |

## 工作原理

1. 守护进程（单一 Go 静态二进制）打开 `/dev/watchdog`，按设定周期（默认 10s）做一组健康检查并"喂狗"。
2. 健康检查项（均可在页面开关/调阈值）：
   - **fork 存活**：能否 `fork()` 新进程（内核调度挂死时失败；零误报，默认开）
   - **系统负载**：`/proc/loadavg` 一分钟负载超过阈值（高负载≠死机，**默认关**）
   - **D 状态进程数**：不可中断（`D`）进程数持续超过阈值（典型 I/O 卡死）
   - **内存可用率**：`MemAvailable` 低于阈值（OOM 类死机）
   - **外部命令探针**（**默认关**，端口须与飞牛一致，见页面警告）
3. **维护窗口内绝不判定**：检测到系统升级（dpkg 锁/升级进程）、systemd 关机流程、开机冷却期（默认 5 分钟）→ 只喂狗不判定。
4. 任一检查**连续失败 N 个周期**（默认 18 = 3 分钟）才判定死机，且判定瞬间复查维护窗口：
   - 把**原因 + 系统快照（负载/内存/D 状态进程/运行时间/OOM 内核证据）**写入持久化日志，并记到 `last_reboot_reason`；
   - 尝试优雅 `reboot`；
   - 若系统已冻到 `reboot` 无法执行，**停止喂狗**，由硬件看门狗超时后强制复位（兜底）。
5. 内核若发生 hardlockup，因已开启 `hardlockup_panic=1` + `kernel.panic=10`，会 panic 并 10 秒后自动重启。

## Web 管理页面

通过飞牛桌面图标（iframe）打开，功能：

- **状态总览**：监控开关、看门狗设备状态与类型、负载、D 状态进程数、连续失败计数、上次重启原因、**当前是否处于维护窗口/开机冷却期**、进程 PID。
- **参数配置**（保存即时生效，字段级合并防丢失）：检测/喂狗周期、看门狗超时、连续失败阈值（上限 120）、开机冷却期、Web 端口、自动重启开关、各健康检查项的开关与阈值、探针命令。
- **日志查看**：实时/分页查看运行日志（含每次重启的原因快照）。
- **一键开关**：暂停/恢复监控（暂停时看门狗被安全解除，系统不会自动重启，页面仍可访问以重新开启）。
- **服务控制**：启动 / 停止 / 重启整个进程（停止时安全解除看门狗）。

## 安装（飞牛 fnOS 测试设备）

获取 `.fpk` 两种方式：

- **仓库根目录预编译包**：`com.gzywd.kanmendog.fpk`（随源码一同提交，可直接下载安装）。
- **GitHub Release**：在仓库 Releases 页下载。

飞牛应用中心 → 手动安装（本地 `.fpk`）→ 安装。或开发者方式：

```bash
appcenter-cli install-local com.gzywd.kanmendog.fpk
appcenter-cli start com.gzywd.kanmendog
```

桌面打开"看门狗 KanmenDog"进行配置与监控。

> 建议先在**无重要数据的测试机**上验证，确认各项阈值适合你的负载后再长期开启自动重启。

## 重要风险与说明

- **误重启**：本版本默认策略为零误杀（3 分钟连续异常才判定、维护窗口不判定、负载检查默认关）。若你在页面调激进阈值，风险自负；日志会记录每次重启原因与完整快照。
- **探针端口**：fnOS 新版默认管理端口是 **5666**（HTTPS 5667），旧版 8000/8001，**80 只是可选重定向**。安装时会自动探测并预填探针命令；开启探针前务必在页面核对端口，填错会在约 3 分钟后误判重启。
- **nowayout 内核**：若看门狗驱动以 `nowayout` 编译，magic close 无效，停止服务后超时仍会硬复位（罕见，多数发行版默认关闭 nowayout）。安装日志会提示。
- **无硬件看门狗的设备**：安装时会尝试加载 `iTCO_wdt`（硬件）/ `softdog`（软件）。若只有 `softdog`，它依赖内核时钟，**内核全冻结时无法复位**，只能覆盖软死机与单核 lockup（已配合 `kernel.panic=10`）。是否具备硬复位能力，请见下方"死机覆盖能力"一节，并在 Web 页面确认看门狗状态。
- **卸载**：会停止服务（先安全解除看门狗）、移除 systemd 单元、按备份**逐项恢复全部四个内核参数**（幂等；备份丢失时恢复 Debian 默认值，避免残留）；`PKGVAR` 下的日志予保留以便排查。

## 死机覆盖能力（必须了解）

本程序**不能保证 100% 覆盖所有死机**。它由两部分互补组成：用户态守护进程负责"软死机"的判断与 `reboot`，内核硬件看门狗负责"硬死机"的强制复位。

### ✅ 能覆盖

- **守护进程自身卡死 / 被 OOM 杀掉**：停止喂狗 → 硬件看门狗超时强制复位（前提：主板有硬件看门狗）。
- **应用 / 服务层 hang**（已配置外部探针时）、**大量 D 状态进程（I/O 卡死）**：用户态健康检查判断到并调用 `reboot`（默认 3 分钟确认窗口）。
- **单核 hardlockup**（某核中断超过 20s，其它核仍正常）：用户态检测**感知不到**，但已开启 `hardlockup_panic=1` 且 `kernel.panic=10`，内核会 panic 并在 10 秒后自动重启。
- **全核内核冻结**（ping 不通、SSH 断、显示卡死）：用户态全冻、判断不了，但硬件看门狗是**独立于内核的硬件定时器**，仍会倒计时并在超时后强制复位。

### ⚠️ 救不了（固有限制，任何软件无解）

- **无硬件看门狗且内核全冻结**：`softdog` 依赖内核时钟，冻结后定时器不再递减，无法复位。能加载 `iTCO_wdt` 等硬件看门狗的 x86 主板才具备硬复位能力。
- **BIOS / 固件级死机、CPU / 内存物理损坏、供电异常**：超出操作系统能力，需**带外方案**（智能插座 / ESP32 在仍可得知"机器无响应"的网络侧物理断电）。
- **看门狗硬件本身故障**：极少见，同上需带外兜底。

### 确认你的设备是否具备硬复位能力

安装后打开 Web 页面查看"看门狗设备状态"与"看门狗类型"：显示已开启（`/dev/watchdog`）即具备；若显示"打开失败 / 无看门狗"，说明该设备无可用硬件看门狗，只能覆盖软死机与单核 lockup，**全核冻结将无法自动恢复**。

> 机型参考：惠普 EliteDesk 800 G5 SFF 基于 Intel 商用芯片组（Q370 系），**基本确定自带 `iTCO_wdt` 硬件看门狗**。安装后状态页"看门狗类型"应显示硬件看门狗；若意外显示"软件软狗/无设备"，需排查 BIOS 是否禁用看门狗或模块加载失败（安装日志会打印身份）。

### 针对 OOM 场景的覆盖（证书重载 → Nginx 崩溃循环 → 日志刷屏 → OOM）

- **默认开启"内存可用率检查"**：可用内存 < 2% 且持续 3 分钟才判定异常 → 主动 `reboot`。page cache 可回收内存不计入耗尽，大拷贝/scrub 不会误杀。
- **可选"飞牛本地 Web 探针"**（默认关）：安装时自动探测端口预填命令；飞牛 Web 无响应（而非返回错误码）才算失败。开启前务必核对端口。
- 若本进程被 OOM killer 杀掉：systemd 拉起、停止喂狗 → 看门狗（硬件或软）超时强制复位兜底。

### 日志与趋势（复盘找真因——最重要）

死机后不要只关心"有没有重启"，**完整日志才能定位根因**。本程序分层记录：

- `kanmendog.log`（持久化于 `PKGVAR`，重启不丢）：每次健康检查失败原因；判定死机时的**系统快照**（内存 MemTotal/Available/Free/Swap、top 内存进程、`dmesg` 中的 OOM / "Killed process" 证据、运行时间）；维护窗口进入/退出记录。
- `trend.csv`（周期性，默认每 5 个周期一行）：`时间, 内存已用%, 可用MB, 负载, D状态数, 进程数, OOM标记`。**重启后读出即可看到"内存从 X% 一路涨到 100% → OOM"的曲线**，定位是谁在吃内存（如 Nginx 崩溃循环刷日志）。
- `last_reboot_reason`：上次重启的结构化原因，状态页直接展示。

建议死机恢复后先做两件事：① 打开 Web 页面看"上次重启原因"；② 导出 `trend.csv` 看内存爬升曲线，结合 `oom_kernel_log` 确认是否 Nginx 被 OOM kill。
- 看门狗超时（默认 60s）应明显大于检测周期，避免正常抖动误触发复位。
