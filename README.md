# 看门狗 KanmenDog

检测 **飞牛 fnOS（x86）死机并自动重启**的看门狗守护进程。当系统卡死（必须手动拔电才能恢复）时，由**内核看门狗硬件**强制复位；同时提供 **Web 管理页面**，可在浏览器里自定义检测参数、查看日志、一键开关。

> 仓库：https://github.com/gzywd/kanmendog ｜ 飞牛应用标识：`com.gzywd.kanmendog`

---

## 为什么需要它

真正的"硬死机"时，同一台机器上的任何用户态脚本也跑不动——它自己也被冻住了。唯一的可靠手段是**独立于内核调度的硬件定时器**：用户态守护进程定期"喂狗"，一旦卡死不再喂狗，硬件看门狗倒计时归零就强制重启。

本应用严格复用飞牛底层系统已有的"轮子"，不重复造：

| 轮子 | 作用 |
|---|---|
| 内核看门狗 `/dev/watchdog`（`iTCO_wdt` 硬件 / `softdog` 软件） | 终极复位，独立于内核调度 |
| systemd（`Restart=always`） | 守护进程挂了自动拉起（飞牛自带机制） |
| 内核 lockup 检测 `softlockup_panic`/`hardlockup_panic` | 把内核级卡死转成 panic → 触发看门狗复位 |
| `/proc/loadavg`、`/proc/*/stat`、`fork` | 健康检查标准原语 |

---

## 工作原理

1. 守护进程（单一 Go 静态二进制）打开 `/dev/watchdog`，按设定周期（默认 10s）做一组健康检查并"喂狗"。
2. 健康检查项（均可在页面开关/调阈值）：
   - **fork 存活**：能否 `fork()` 新进程（内核调度挂死时失败）
   - **系统负载**：`/proc/loadavg` 一分钟负载超过阈值
   - **D 状态进程数**：不可中断（`D`）进程数超过阈值（典型 I/O 卡死）
   - **外部命令探针**（可选）：自定义命令须返回 0，否则判定异常
3. 任一检查**连续失败 N 次**（默认 3 次）判定死机：
   - 把**原因 + 系统快照（负载/内存/D 状态进程/运行时间）**写入持久化日志 `TRIM_PKGVAR/log/kanmendog.log`，并记到 `last_reboot_reason`，便于事后排查；
   - 尝试优雅 `reboot`；
   - 若系统已冻到 `reboot` 无法执行，**停止喂狗**，由硬件看门狗超时后强制复位（兜底）。
4. 内核若发生 soft/hard lockup，因已开启 `*_panic=1`，会触发 panic，同样落到看门狗复位。

## Web 管理页面

通过飞牛桌面图标（iframe）打开，功能：

- **状态总览**：监控开关、看门狗设备状态、当前负载、D 状态进程数、连续失败计数、上次重启原因、进程 PID。
- **参数配置**（保存即时生效）：检测/喂狗周期、看门狗超时、连续失败阈值、Web 端口、自动重启开关、各健康检查项的开关与阈值、可选探针命令。
- **日志查看**：实时/分页查看运行日志（含每次重启的原因快照）。
- **一键开关**：暂停/恢复监控（暂停时看门狗被安全解除，系统不会自动重启，页面仍可访问以重新开启）。
- **服务控制**：启动 / 停止 / 重启整个进程。

## 安装（飞牛 fnOS 测试设备）

获取 `.fpk` 两种方式：

- **仓库根目录预编译包**：`com.gzywd.kanmendog.fpk`（随源码一同提交，可直接下载安装）。
- **GitHub Release**：在仓库 Releases 页下载（若已发布；标签 `v1.0.0` 已打）。

飞牛应用中心 → 手动安装（本地 `.fpk`）→ 安装。或开发者方式：

```bash
appcenter-cli install-local com.gzywd.kanmendog.fpk
appcenter-cli start com.gzywd.kanmendog
```

桌面打开"看门狗 KanmenDog"进行配置与监控。

> 建议先在**无重要数据的测试机**上验证，确认各项阈值适合你的负载后再长期开启自动重启。

## 从源码构建 .fpk

```bash
# 1) 编译二进制（静态，linux/amd64）
cd src/kanmendog
GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build -o ../../app/kanmendog .
cd ../..

# 2) 打包（脚本会自动下载 fnpack）
bash scripts/build.sh
# 产物：kanmendog-1.0.0.fpk
```

## 重要风险与说明

- **误重启**：NAS 上有数据，错误判定会中断存储服务。默认阈值偏保守（连续 3 次失败、负载阈值 16、D 状态 20），请按实际负载调整；日志会记录每次重启原因。
- **无硬件看门狗的设备**：安装时会尝试加载 `iTCO_wdt`（硬件）/ `softdog`（软件）。若只有 `softdog`，它依赖内核时钟，**内核全冻结时无法复位**，只能覆盖软死机与单核 lockup（已配合 `kernel.panic=10`）。是否具备硬复位能力，请见下方"死机覆盖能力"一节，并在 Web 页面确认看门狗状态。
- **卸载**：会停止服务、移除 systemd 单元与内核参数兜底，并**恢复 `kernel.panic` 原值**（不强行改变整机 panic 行为）；`PKGVAR` 下的日志予保留以便排查。

## 死机覆盖能力（必须了解）

本程序**不能保证 100% 覆盖所有死机**。它由两部分互补组成：用户态守护进程负责"软死机"的判断与 `reboot`，内核硬件看门狗负责"硬死机"的强制复位。

### ✅ 能覆盖

- **守护进程自身卡死 / 被 OOM 杀掉**：停止喂狗 → 硬件看门狗超时强制复位（前提：主板有硬件看门狗）。
- **应用 / 服务层 hang**（已配置外部探针时）、**大量 D 状态进程（I/O 卡死）**：用户态健康检查判断到并调用 `reboot`。
- **单核 softlockup / hardlockup**（某核关抢占 / 中断超过 20s，其它核仍正常）：用户态检测**感知不到**，但已开启 `kernel.softlockup_panic=1` / `hardlockup_panic=1` 且 `kernel.panic=10`，内核会 panic 并在 10 秒后自动重启。
- **全核内核冻结**（ping 不通、SSH 断、显示卡死）：用户态全冻、判断不了，但硬件看门狗是**独立于内核的硬件定时器**，仍会倒计时并在超时后强制复位。

### ⚠️ 救不了（固有限限，任何软件无解）

- **无硬件看门狗且内核全冻结**：`softdog` 依赖内核时钟，冻结后定时器不再递减，无法复位。能加载 `iTCO_wdt` 等硬件看门狗的 x86 主板才具备硬复位能力。
- **BIOS / 固件级死机、CPU / 内存物理损坏、供电异常**：超出操作系统能力，需**带外方案**（智能插座 / ESP32 在仍可得知"机器无响应"的网络侧物理断电）。
- **看门狗硬件本身故障**：极少见，同上需带外兜底。

### 确认你的设备是否具备硬复位能力

安装后打开 Web 页面查看"看门狗设备状态"：显示已开启（`/dev/watchdog`）即具备；若显示"打开失败 / 无看门狗"，说明该设备无可用硬件看门狗，只能覆盖软死机与单核 lockup，**全核冻结将无法自动恢复**。
- 看门狗超时（默认 60s）应明显大于检测周期，避免正常抖动误触发复位。
